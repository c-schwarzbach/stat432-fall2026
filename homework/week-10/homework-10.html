Question 1 — Bias–variance trade-off simulation

1(a). Simulation design and figures

The test predictors are generated once from a five-dimensional multivariate normal distribution with unit marginal variances and pairwise correlation 0.3. They remain fixed across all 100 repetitions. Each repetition generates a fresh training sample of 200 observations. Within a repetition, all tuning settings use the same training sample, so differences between settings are not confounded by different training data. The response is the specified signal plus independent standard normal noise.

For a test point \(x_i\), the estimates are \(\widehat{Bias}^2_i=(\overline{\hat f}_i-f(x_i))^2\) and \(\widehat{Var}_i=R^{-1}\sum_r(\hat f_{ir}-\overline{\hat f}_i)^2\). The plotted quantities average these pointwise estimates over the 200 fixed test points.

library(RLT)
set.seed(43210)

R <- 100
n.train <- 200
n.test <- 200
p <- 5
rho <- 0.3
Sigma <- matrix(rho, p, p)
diag(Sigma) <- 1

# Generate the fixed test set once.
Z.test <- matrix(rnorm(n.test * p), n.test, p)
X.test <- Z.test %*% chol(Sigma)
f.test <- X.test[, 1] + X.test[, 3] + X.test[, 5]

node.values <- c(1, 5, 10, 20, 30)
mtry.values <- 1:5

# Array dimensions: test point x repetition x setting.
pred.node <- array(NA_real_, c(n.test, R, length(node.values)))
pred.mtry <- array(NA_real_, c(n.test, R, length(mtry.values)))

for (r in seq_len(R)) {
  Z <- matrix(rnorm(n.train * p), n.train, p)
  X <- Z %*% chol(Sigma)
  y <- X[, 1] + X[, 3] + X[, 5] + rnorm(n.train)

  # Same training data for every node-size and mtry setting.
  for (j in seq_along(node.values)) {
    fit <- RLT(
      x = X, y = y, model = "regression",
      ntrees = 500, mtry = 3, nmin = node.values[j],
      resample.prob = 1, replacement = TRUE,
      reinforcement = FALSE, importance = FALSE,
      use.cores = 1
    )
    pred.node[, r, j] <- predict(fit, X.test)$Prediction
  }

  for (j in seq_along(mtry.values)) {
    fit <- RLT(
      x = X, y = y, model = "regression",
      ntrees = 500, mtry = mtry.values[j], nmin = 10,
      resample.prob = 1, replacement = TRUE,
      reinforcement = FALSE, importance = FALSE,
      use.cores = 1
    )
    pred.mtry[, r, j] <- predict(fit, X.test)$Prediction
  }
}

summarize_pred <- function(pred, truth, tuning) {
  b <- v <- numeric(dim(pred)[3])
  for (j in seq_len(dim(pred)[3])) {
    point_means <- rowMeans(pred[, , j])
    b[j] <- mean((point_means - truth)^2)
    v[j] <- mean(apply(pred[, , j], 1, function(z) mean((z - mean(z))^2)))
  }
  data.frame(setting = tuning, squared_bias = b, variance = v)
}

node.results <- summarize_pred(pred.node, f.test, node.values)
mtry.results <- summarize_pred(pred.mtry, f.test, mtry.values)

# Two separate figures, as requested.
plot_bias_variance <- function(d, xlab, main) {
  matplot(d$setting, cbind(d$squared_bias, d$variance),
          type = "b", pch = c(16, 17), lty = 1,
          xlab = xlab, ylab = "Average over 200 test points",
          main = main, col = c("#24618a", "#c16b32"))
  legend("topright", c("Squared bias", "Variance"),
         col = c("#24618a", "#c16b32"), pch = c(16, 17), lty = 1)
}
par(mfrow = c(1, 1))
plot_bias_variance(node.results, "Node size (nmin)", "Bias–variance vs. node size")
plot_bias_variance(mtry.results, "mtry", "Bias–variance vs. mtry")

print(node.results)
print(mtry.results)

1(b). Interpretation

Large node size. A larger minimum node size restricts how finely each tree can partition the predictor space. In this example, a node size of 30 is relatively large compared with the training sample of 200. The resulting trees are shallower and smoother. This can reduce variance because individual trees are less sensitive to the particular training sample, but it can increase bias because the trees cannot represent the additive regression surface as flexibly. The simulation curves should be used to determine how pronounced this effect is for this sample size and signal.

Large mtry. A larger mtry gives each split more candidate predictors. This makes it more likely that useful variables (\(X_1,X_3,X_5\)) are available, which can improve split quality and reduce bias. However, trees may become more similar because they repeatedly have access to the same strong predictors. Greater similarity reduces the variance-reduction benefit of averaging many trees. A smaller mtry increases tree diversity, but may often leave a useful predictor out of the candidate set and weaken individual splits. The best choice balances split strength and diversity.

Sampling 100 rather than 200 observations per tree. I would expect the preferred node size to tend toward a smaller value, although this is not guaranteed. With fewer observations in each tree's bootstrap sample, a fixed node-size threshold of 10 or 20 is a larger fraction of the available data and can force trees to be too shallow. Reducing the threshold allows each tree to grow more deeply and may recover some flexibility. The smaller samples also make individual trees noisier, so the extra flexibility can increase variance; the preferred value should therefore be checked empirically rather than assumed.

The first 1,000 rows are used only to construct the training subset, and the second 1,000 rows only to construct the test subset. PCA is estimated from training pixels only, with centering and no scaling. Test scores use the training center and loading matrix, preventing information leakage from the test observations.

2(b). Grid search and OOB permutation importance

The grid below covers a range of candidate split-variable counts and node sizes. Each fit uses 1,000 trees and bootstrap samples of the same size as the filtered training set. Select the pair with the smallest OOB misclassification rate. Ties should be resolved consistently (for example, choose the larger node size to favor a simpler forest).

# Candidate values; report and justify the grid you use.
mtry.grid <- c(2, 4, 6, 8, 10, 15, 20)
nmin.grid <- c(1, 5, 10, 20, 30)

# Helper for the RLT version installed in your course environment.
# Inspect AllError once to confirm which element is the final OOB
# classification error; update this extractor if your version stores
# the error in a differently named component.
get_final_oob <- function(fit) {
  z <- fit$AllError
  if (is.null(z)) stop("AllError is missing; check RLT importance/OOB settings.")
  if (is.numeric(z) && is.null(dim(z))) return(tail(z, 1))
  if (is.matrix(z) || is.data.frame(z)) {
    numeric.cols <- which(vapply(as.data.frame(z), is.numeric, logical(1)))
    if (!length(numeric.cols)) stop("No numeric OOB-error column found.")
    return(as.numeric(z[nrow(z), numeric.cols[1]]))
  }
  stop("Unrecognized AllError structure; inspect str(fit$AllError).")
}

grid <- expand.grid(mtry = mtry.grid, nmin = nmin.grid)
grid$oob.error <- NA_real_
fits <- vector("list", nrow(grid))

for (i in seq_len(nrow(grid))) {
  fits[[i]] <- RLT(
    x = X.train, y = y.train, model = "classification",
    ntrees = 1000, mtry = grid$mtry[i], nmin = grid$nmin[i],
    resample.prob = 1, replacement = TRUE,
    reinforcement = FALSE, importance = FALSE
  )
  grid$oob.error[i] <- get_final_oob(fits[[i]])
}

grid <- grid[order(grid$oob.error, -grid$nmin), ]
print(grid)

best <- grid[1, ]
cat("Selected mtry:", best$mtry, "\n")
cat("Selected node size:", best$nmin, "\n")
cat("Selected OOB error:", best$oob.error, "\n")

# Refit selected setting with OOB permutation importance enabled.
importance.fit <- RLT(
  x = X.train, y = y.train, model = "classification",
  ntrees = 1000, mtry = best$mtry, nmin = best$nmin,
  resample.prob = 1, replacement = TRUE,
  reinforcement = FALSE, importance = "permute"
)
cat("OOB error of the refit used below:", get_final_oob(importance.fit), "\n")
print(importance.fit$VarImp)
barplot(as.vector(importance.fit$VarImp),
        names.arg = paste0("PC", 1:20), las = 2,
        ylab = "OOB permutation importance",
        main = "Permutation importance of the first 20 PCs")

How to comment on importance: Identify which principal components have the largest permutation importance and whether importance is concentrated in a few components or spread across many. A larger value means that permuting that component harms OOB classification more. Principal components are linear combinations of the original pixels, so “PC1 is important” does not mean one particular pixel is important. Also note that neighboring PCs can share or distribute predictive information.

Question 3 — Planning a random-forest analysis skill

3(a). Paragraph

I would write the skill as a concise, reusable workflow that establishes the essential standards of a sound random-forest analysis while leaving data-dependent choices to the AI. The skill should require the AI to inspect the data, identify the response and predictors, check missingness and class balance, separate training and assessment data appropriately, fit a random forest, tune important hyperparameters using a clearly defined validation or out-of-bag criterion, and evaluate the final model on data not used for tuning. These steps protect the validity and reproducibility of the analysis and should not be left to guesswork. However, I would not prescribe one fixed tuning grid, one set of plots, or one interpretation for every dataset. A capable AI can adapt those choices to the sample size, number and type of predictors, response type, and computational limits. I would use the skill to specify my preferences—such as a reproducible seed, readable tables, clearly labeled figures, concise explanations, and explicit discussion of limitations—while asking the AI to explain any dataset-specific decisions. For a less capable AI, I would add more detailed step-by-step guidance and examples; for a capable AI, I would keep standard statistical instructions brief and focus the skill on requirements that are easy to overlook or that reflect my preferred reporting style.

3(b). Ten instructions, from basic to personal preferences

  1. Identify the response variable and predictor variables, and determine whether the task is classification or regression.
  2. Inspect the dataset dimensions, variable types, missing values, outcome distribution, and any potential data-quality problems before fitting a model.
  3. Separate training data from validation or test data before model development; do not use the final test labels to tune the model.
  4. Fit an appropriate random-forest model and state the software, package, key settings, and random seed used.
  5. Tune relevant hyperparameters, including the number of candidate predictors per split and the minimum terminal-node size, using a clearly stated validation or OOB criterion.
  6. Compare the tuned model with a reasonable baseline and report an appropriate performance measure, such as misclassification rate for classification or RMSE for regression.
  7. Include a clearly labeled table of tuning results and identify the selected model and the criterion used to select it.
  8. Include useful figures, such as tuning-performance plots and variable-importance plots, with readable labels, units, and captions.
  9. Interpret the results in plain language, distinguish association or predictive importance from causation, and discuss uncertainty, limitations, and possible overfitting.
  10. Use a clean, consistent report style: state the main findings first, round numerical results consistently, avoid unnecessary technical detail, and make all code and analysis steps reproducible.
